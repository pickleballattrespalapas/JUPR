## A) Migration system discovery

### How migrations are run in this repo
- `make db-migrate` invokes `scripts/db_migrate.sh`.
- `scripts/db_migrate.sh` applies SQL files from **`migrations/*.sql`**, not `supabase/migrations/*.sql`.
- This indicates a split between current migration source (`supabase/migrations`) and an older runner path (`migrations`).

## C) Static DDL consistency checks

Checker implemented in `scripts/audit_migrations.py`:
- Auto-discovers migration roots (`supabase`, `migrations`, and placeholders for prisma/alembic discovery).
- Orders migration files by filename.
- Parses SQL (regex-based) for:
  - `CREATE SCHEMA`
  - `CREATE TABLE`
  - `DROP TABLE`
  - `ALTER TABLE`
  - `ALTER TABLE ... RENAME TO ...`
- Detects and reports:
  - ALTER references to tables unknown at that point
  - ALTER references to dropped tables
  - ALTER references old names after rename

### Key static results
- **Strict empty-db model (migrations only):** 40 violations in `supabase/migrations`, including 38 `alter_missing`; first is `20250301_player_inactivity.sql` on `public.players`.
- **Snapshot-seeded model** (using `docs/schema/live_schema_snapshot_20260219.sql` as pre-existing schema): only 1 violation (`DROP TABLE public.badge_rules_v2` missing in `20260809_cleanup_badge_v2_deprecated_schema.sql`).

Interpretation:
- The migration chain appears to rely on a pre-existing schema baseline not represented as an early migration file in `supabase/migrations`.

## Special investigation: `public.players` missing-table error

Error pattern:
```sql
ERROR: relation "public.players" does not exist (SQLSTATE 42P01)
ALTER TABLE public.players
  ADD COLUMN IF NOT EXISTS last_game_at timestamptz NULL,
  ADD COLUMN IF NOT EXISTS inactive_at timestamptz NULL;
```

### 1) Which migration triggers it?
- `supabase/migrations/20250301_player_inactivity.sql` starts with `ALTER TABLE public.players ...` and is the earliest direct trigger.

### 2) Is `public.players` ever created in migrations?
- In `supabase/migrations/*.sql`, no `CREATE TABLE ... players` found.
- Additional references exist (`ALTER`, `UPDATE`, RLS policies, RPC writes), but no creation migration.

### 3) Was it renamed/dropped earlier?
- No `ALTER TABLE ... RENAME TO ...` involving `players` found.
- No `DROP TABLE ... players` found.
- So there is no migration-local lifecycle event that would explain a normal create→rename/drop chain.

### 4) Does it exist in schema snapshot but not migrations?
- Yes. `docs/schema/live_schema_snapshot_20260219.sql` contains `CREATE TABLE players (...)`.
- This strongly suggests migrations are written assuming a baseline schema already exists.

### 5) Which applied-migrations state leads to this failure?
- Empty DB + apply `supabase/migrations` from first file onward.
- `20250220_badges_v1.sql` applies first; next `20250301_player_inactivity.sql` fails because `public.players` has not been created by earlier migrations.

### Ranked likely root causes + confirmation steps
1. **Missing baseline migration / snapshot not applied** (most likely)
   - Confirm by searching migrations for `CREATE TABLE players` (none).
   - Confirm snapshot contains table definition.
2. **Migrations executed out of order or partially applied**
   - Confirm by inspecting migration tracking table in target DB vs local file list.
3. **Schema mismatch (`players` exists outside `public`)**
   - Confirm with `information_schema.tables` by schema.
4. **Table renamed/dropped earlier**
   - Low likelihood given no migration evidence; confirm by scanning history and DB catalog.
5. **Environment drift/manual DB changes**
   - Confirm by diffing live schema and applied migration records against repo.

---

## Diagnosis summary

- The repo contains a strong indicator of baseline-dependent migrations: many `ALTER TABLE` statements target tables not created earlier in migration order.
- `public.players` failure is consistent with applying `supabase/migrations` to a true empty DB without an initial schema bootstrap.
- There is also migration-runner drift: `make db-migrate` targets `migrations/`, while most active SQL is under `supabase/migrations/`.
