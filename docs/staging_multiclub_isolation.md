The 60 matches span six weeks. Player and league ratings, win/loss counts and
rating snapshots agree with that history. Ratings use the existing JUPR
calculation. **Isolation Test Ladder**, **Isolation Test Draft**, and
**Isolation Test Cup** deliberately have the same names at all three clubs.
Their records, rosters and IDs are separate.

## Try the club boundaries

1. Open **La Ribera → Players** and find **Alex Rivera [TEST]**. Repeat in Cabo
   and La Paz. The names match, but the player IDs, ratings and match histories
   differ. Six names and six fictional contact addresses are intentionally
   repeated across clubs.
2. Change Alex's rating or active status in one workspace. Switch clubs and
   confirm the other copies retain their previous values. You can also add a
   new player in one club and search for that name in the others.
3. Open **Match Log**, **League Manager**, and **Tournament Manager** after each
   switch. The names of the sample programs match; their participants and
   records must belong to the selected club. Try editing a draft league or a
   tournament team and then checking the other clubs' copies.
4. In a public player or match link, substitute another club's slug while
   keeping the player/match ID. That object must be unavailable. A foreign
   player's match-history endpoint must return no matches.
5. Leave an admin page open in a second tab, switch clubs in the first tab,
   then return to the older tab. Refresh its club context before making edits;
   an old selection must not silently operate in the newly selected club.

## Verification and reproducibility

The fixture is generated by `scripts/prepare_multiclub_isolation_fixture.py` and
`scripts/fixtures/multiclub_isolation.sql`. Generation rejects any project other
than `sijpxjxvdtrehmqvirfi`. The SQL also requires the existing synthetic staging
sentinel. It creates the new clubs through the guarded invitation and verified
acceptance functions. The seed commits atomically, refuses unrelated target
data, and becomes a no-op once the fixture exists, preserving manual edits.

Completed verification includes:

- A rollback-only seed rehearsal, then the committed fixture transaction.
- Exact preservation of existing Tres players, matches, leagues, tournaments,
  and season drafts using before/after database fingerprints.
- Zero cross-club references in match participants, league rosters, player
  contacts, tournament teams and interclub rosters.
- Live guarded-transaction checks: six rejected foreign-player submissions,
  six rejected foreign-team edits, three rejected inactive-player submissions,
  and three successful substitutions that left other teams/meets unchanged.
  Every probe was rolled back.
- Focused service/API tests for separate directories, same-name league rosters,
  scoped player edits, single-club authorization, and interclub contact filtering.

`scripts/verify_multiclub_public_isolation.py` checks the deployed staging API's
club lists, match history, public profiles, same-name league results and foreign
object URLs. It makes GET requests only, checks staging identity, and rejects a
deployment change mid-run. It expects the original fixture counts; manual
testing can legitimately change those counts. The SQL verification script also
expects the original roster revisions and upcoming meets.

Authenticated browser switching and independent single-club-account acceptance
remain manual checks. The automated authorization tests cover the single-club
permission rules; this fixture uses one account assigned to all three clubs.
