# API timing evidence

`request.complete` and `request.failed` retain one JSON record per request. The
record includes a request ID, matched route template, machine ID when on Fly,
status, and overall elapsed milliseconds. Query strings, dynamic path values,
SQL, Supabase filters, request bodies, and responses are not added to these
records. Unmatched routes use `<unmatched>`.
Requests rejected before routing use the registered route template when one
matches, without executing the endpoint. Non-SDK compatibility clients supplied
by local tools/tests retain their identity and capabilities.

## Measurements

| Field | Meaning |
| --- | --- |
| `elapsed_ms` | API middleware start to response headers, including handler scheduling; not full browser page load or streaming-body duration. |
| `db_calls`, `db_errors` | Completed or failed Supabase `execute()` operations through the request-owned client adapter, including RPCs and writes. An SDK retry remains one execute operation. |
| `db_elapsed_ms` | Sum of client-side execute elapsed times: network, server wait, response transfer/decoding and client work. This is not PostgreSQL-only time. |
| `db_thread_cpu_ms` | Sum of CPU consumed by the executing thread during those operations; excludes CPU used by other API threads. |
| `phases.<name>.calls` | Number of instrumented synchronous calculation phases. |
| `phases.<name>.elapsed_ms` | Sum of elapsed time in the named phase. |
| `phases.<name>.thread_cpu_ms` | Sum of current-thread CPU time in the named phase. |

Only code-owned phase names are accepted. The request accumulator is bounded by
that allowlist and is shared safely into FastAPI's sync worker threads. Background
clients without a request context remain untouched. Auth/storage calls, direct
SDK clients created outside the API factory, and work after response headers are
not covered by the database totals.

Compare the same request's timings, then correlate its machine and timestamp with
Fly's CPU quota balance, throttle and memory graphs. Large client DB elapsed time
with small Supabase upstream service time points to work or waiting outside that
upstream interval; it does not by itself locate the delay. A calculation phase's
thread CPU distinguishes CPU actually consumed from its wall time, but the
difference can include scheduling, locks, and other waits.

Do not subtract or add these fields into an exclusive percentage breakdown:
parallel calls and nested phases can overlap. Uninstrumented calculation,
thread-pool queue wait, and throttling attribution remain unknown. Generator
process timing remains a separate `jupr.api.compute` event; its `cpu_ms` is worker
process CPU, not API request CPU. Worker lifecycle events use `jupr.badge.worker`
and may be correlated in time, but must not be counted as public request work.

Validation uses a real Supabase/PostgREST query chain with an in-memory HTTP
transport, concurrent ASGI requests that execute in separate sync threads, a real
local Uvicorn process using the shipped log config, and failure-path/privacy
checks. No production traffic is generated by these tests.
